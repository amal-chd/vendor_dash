# Production outage found 2026-10-05: two faults left by the asia-south1 move

Both were introduced on **2026-10-03** and were still live when found. Neither is
visible in `firebase functions:list`, which happily lists a function that cannot
serve a single request — which is why they went unnoticed.

---

## Fault 1 — 104 callables reject every request with 403 before they run

**Evidence (first-hand):** reading each service's Cloud Run IAM policy shows
104 of the 152 callable/HTTPS functions have **no bindings at all**.
`advanceDeliveryStage` and `reassignDelivery` return an empty policy;
`searchStays` still has `allUsers`. A request to `reassignDelivery` and to
`advanceDeliveryStage` returned a bare `403 Forbidden` HTML page from Google's
front end — not a function response.

**Why it breaks everything:** a Firebase client calls a callable with a Firebase
ID token, which is not a Google IAM identity. The invoker check can therefore
only be satisfied by `allUsers`, which is what `firebase deploy` sets. With no
binding, the front end refuses the request before the container starts, so the
function's own auth never runs and **nothing appears in its logs**.

Among the 104: `acceptDeliveryOffer`, `completeDelivery`, `createRazorpayOrder`,
`calculatePricing`, `calculateDeliveryFee`, `createStayBooking`,
`checkAvailability`, `advanceDeliveryStage`, `reassignDelivery`. That is
ordering, paying, delivering and booking.

**Restoring the binding is not a security loosening** — authorisation happens
inside each function (`request.auth`, `assertAdmin`, `resolveVendorActor`).
Without it, legitimate signed-in users are refused along with everybody else.

**Fix:**

```bash
bash scripts/restore_callable_invokers.sh
```

**Re-run this after ANY redeploy of a callable that was broken.** `firebase
deploy` sets the invoker binding when it *creates* a function, never when it
*updates* one — proven twice: `advanceDeliveryStage` still had an empty policy
after a redeploy, and the four mess functions came back `ready=True` with no
binding at all, because the CLI logged "updating" (their Firebase registry
entries still existed) and so never touched IAM.

Status 2026-10-06: run by the user — **100 of 104 bound**, verified
independently with `node scripts/doctor.mjs --online --all-invokers`
(148/152 callables invokable). The 4 that failed were the mess functions in
fault 3, which had no service to bind to.

Scope is deliberately limited to callables and HTTPS endpoints. Scheduled
functions and Firestore triggers are invoked with service-account identities and
must stay private; none are in the list. Full list:
`docs/outage-2026-10-03-missing-invoker.txt`.

## Fault 3 — the whole Kada Mess surface was dead (fixed 2026-10-06)

`subscribeToMess`, `verifyMessPayment`, `skipMessDay` and
`cancelMessSubscription` were in `STATE: FAILED` with `CloudRunServiceNotFound`
— "Cloud Run service ... was not found. The function will not work correctly.
Please redeploy." Their backing services had been deleted during the
migration's partial delete pass while the Firebase registry entries survived,
so nobody could subscribe to a mess plan, pay for one, skip a day or cancel.

`firebase functions:list` listed all four as healthy callables. Only
`gcloud functions list --filter="state:FAILED"` revealed it — worth adding to
any post-migration check.

Redeployed: three landed on the first pass; `cancelMessSubscription` hit the
CPU quota and **succeeded on an immediate retry**, which is the useful lesson
about fault 2 below — the ceiling fluctuates, so retry a small batch rather
than treating it as a wall. All four are now `Ready` and zero functions remain
in FAILED state. They still need the invoker binding (see above).

## Fault 2 — 81 functions have no serving revision (CPU quota)

**Evidence (first-hand):** 81 of 208 Cloud Run services report
`Ready: False`, each with:

> Quota exceeded for total allowable CPU per project per region.

timestamped 2026-10-03, reason `HealthCheckContainerError`, with the previous
revision marked `Retired` — so there is no revision left that can serve.

**The arithmetic.** Summing `cpu × maxInstances` over what is deployed:

| cpu | maxInstances | services | vCPU |
|-----|--------------|----------|------|
| 0.5 | 1 | 134 | 67.0 |
| 0.5 | 2 | 21 | 21.0 |
| 0.5 | 3 | 18 | 27.0 |
| 0.5 | 5 | 7 | 17.5 |
| 1.0 | 1 | 28 | 28.0 |
| **total** | | **208** | **160.5** |

The 127 healthy services already reserve **93 vCPU**; the 81 failing ones need
**67.5 vCPU** more. The region's ceiling sits between those, so roughly 40% of
the platform cannot hold a revision. Functions at `cpu: 1` are the `HOT_PATH`
set (checkout, payments, delivery) — the ones that must stay fast.

Affected includes `onOrderPlacedAssignRider` (no rider is auto-assigned),
`notifyVendorNewOrder` (the restaurant is never told), `submitOnboarding` /
`submitBankDetails` (no partner can onboard), `searchStays`,
`generateVendorSettlements`, `sweepStuckDeliveries`, and
`onOrderFinishedEnsureEarnings` (the rider-earnings safety net). Full list:
`docs/outage-2026-10-03-no-serving-revision.txt`.

**Two levers — this is a judgement call, not a mechanical fix:**

1. **Raise the quota.** Request an increase for *Total CPU allocation* in
   `asia-south1` (Cloud Run) to ~200 vCPU. Needs a console/support request. This
   is the only option that keeps current sizing.
2. **Cut the reservation to fit.** Keep `HOT_PATH` at `cpu: 1` (28 vCPU) and
   drop the long tail to `cpu: 0.25` with non-hot `maxInstances` capped at 2:
   roughly **84.5 vCPU total**, which fits under the current ceiling. Costs
   cold-start speed on the long tail and needs a redeploy of ~180 functions.

**Redeploy in batches either way.** A mass deploy is what caused this: the CLI
creates every new revision before the old ones retire, so the peak reservation
is momentarily doubled. Deploying six functions at a time worked fine today.
